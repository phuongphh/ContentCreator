# ContentCreator — Dev/Production operations

Production runs on this Mac Mini in the checkout `~/ContentCreator`; the live bot/schedules and content DB are real user workloads. There is no active VPS Production. **Production is exactly one commit of `main`:** the checkout's `HEAD` with no tracked file modified. Untracked runtime files (`.env`, OAuth/client-secret/token files, the SQLite DB, media, caches, logs) belong to the host and are never touched by a deployment. Fleet registers this checkout as `runtime_kind: git_checkout` and measures it itself (`fleet production-state ContentCreator`); a version written in a receipt never replaces that measurement.

## Dev preparation

Stage only the approved SHA in a new isolated directory, without `.env`, OAuth/client-secret/token files, DB, logs, media outputs or live launchd definitions. Use a fresh Dev DB initialized by the existing application migrations. `python ops/fleet/verify_dev.py <dev-db>` verifies integrity, exact candidate migration versions, required column definitions and indexes **read-only**. It builds a disposable reference DB using the real migration runner with a stub config, without loading dotenv or provider credentials. It intentionally reports user_path/services/publishing_guard as incomplete: schema success alone is not a usable Dev release.

Register a separate Dev workspace, data/cache/output roots and service labels. Start no live bot, scheduler, uploader or publishing/approval endpoint. Real credentials must not be inherited from the shell or loaded from a parent/live `.env`; use synthetic data and local preview first. A Telegram user-path test needs a separately provisioned Dev bot/channel, not the real publishing bot. Any provider-backed generation requires its own explicit authorized credentials and cost budget.

Readiness checks: artifact, isolation, database, services, user_path and publishing_guard. Validate an actual preview corresponding to the changed feature, show where the PO can inspect it, and demonstrate publishing is disabled before inviting Dev acceptance. Keep dev_batch off until the isolated runtime and these checks have been observed.

## Production activation and rollback

**Use `ops/deploy.py`; do not run the steps below by hand.** It reads the commits and the database and runs the steps in this fixed order, so a plan cannot forget a migration or pick a forbidden rollback (23/11: a hand-written plan said the new migration "runs at startup" and rolled back with `git reset --hard` plus the old database). Run it from the Production checkout with the system `python3`:

- `python3 ops/deploy.py plan <sha> --fetch`: read-only. Production commit, hand-edited files, migrations still to apply on the real DB, plist/requirements changes, the exact steps, the rollback command and whether now is a scheduled-work window (06:00–07:30, 23:25–23:45). Its JSON output is the preparation evidence.
- `python3 ops/deploy.py apply <sha>`: refuses on hand edits, a non fast-forward or a busy window; refuses while a scheduled job is running; stops the bot and pauses the scheduled jobs; backs up the DB with the SQLite backup API to `~/ContentCreator-backups/<time>-<sha>/`; `git merge --ff-only`; installs requirements when they changed; `python -m storage.migrate up` when a migration is pending; `launchd/install.sh`; then `verify`. If anything fails before the restart it puts the code back on the previous commit and restarts, so Production is never left down or half-moved.
- `python3 ops/deploy.py verify <sha>`: read-only. Checkout exactly at `<sha>` with no hand edit, every migration of that commit recorded in `_migrations`, bot running, every plist loaded. Exit code 0 only when all hold.
- `python3 ops/deploy.py rollback <previous-sha>`: code only, `git checkout --detach`; reports migrations the database keeps from the newer code. The database is never restored by it.

CI runs all four on a copy of this repository with a real database (`content-pipeline/tests/test_ops_deploy.py`). The text below is what the command does and why.

After Dev acceptance and separate Production approval of an exact commit, check that Production measures at the recorded baseline commit with no hand-edited tracked file (Fleet refuses `release-readiness` and `release-claim` otherwise). Record the affected `com.ai5phut.*` labels, pause the relevant publishing/queue/bot jobs, confirm no active write/upload and create a consistent SQLite backup. Then move the checkout with Git only: `git fetch origin` and `git merge --ff-only <approved-sha>`. Git refuses when a tracked file was edited by hand: stop and report it, never force, stash, reset or clean. Run `python -m storage.migrate up` from `content-pipeline/` when the release adds a migration, re-run `launchd/install.sh` when it adds or changes a plist, rebuild the virtualenv when `requirements.txt` changed, and restart only the affected labels following the brain runbook `products/content-creator/_ops/restart`. Verify logs, the actual bot command/preview path and resumption of the intended schedules; Fleet refuses `release-deployed` until the checkout measures exactly at the approved commit. Do not publish a real test video to prove deployment without explicit approval.

If a check fails, do not announce success. Roll code back with `git checkout --detach <previous-sha>` (the baseline in the release record) while services are quiescent, then restart and recheck the user path; Fleet then reports Production at the previous commit until a release or the owner's approval records it. Preserve all content/queue writes and publishing receipts; a code rollback must not reset successful uploads or cause duplicate posts. Database rollback is a separate data decision (below).

## Delivery contract

PM owns requirements/issues and PO communication; the coding worker proposes code and stops at a PR. The PO merges. DevOps operates deployments only after a separate version-bound approval. A merge, passing CI, generated plan or health-only check is not deployment or owner acceptance.

A release ships everything merged to its commit: there are no partial releases. A change that must not ship is reverted on `main` by PR, or an older commit is released. Dev still stages reviewed code from Git objects by full SHA into its own isolated directory; nothing stages files into the live checkout. Host paths, service identifiers and credentials stay in private host bindings outside Git. `ops/fleet/**` is a maintenance path: normal coding workers cannot modify this adapter to grant themselves execution.

Before activation, DevOps confirms the measured baseline, verifies candidate CI, obtains exact version/environment approval, establishes quiescence and backs up the database. Move the checkout to the approved commit, restart only affected services, run all project readiness checks, then record `release-deployed` with the receipt.

Fleet's monitor measures the checkout after each operator handoff closes and once a day, and tells the owner when it differs from the last recorded commit. Only the owner's approval code (`fleet production-state ContentCreator --apply --approve <code> --owner-reference …`, run by DevOps) records a commit Fleet did not release; a state with hand-edited tracked files is never recorded. Database rollback is a separate data decision: never restore an older DB after new writes without reconciliation. Keep deployment history, approval references and recovery evidence.

## Interactive Dev approval (no publishing)

`prepare_dev.py <SHA-pinned-artifact> --state <new-private-dir> --output <new-compose.json>` prepares a dedicated `fleet-content-dev` service. Start only that compose project after the version/environment approval. The existing Streamlit UI is available on `http://127.0.0.1:18866`; it uses actual migrations and review-service state transitions with synthetic videos. The Dev button is **Duyệt thử**. It never posts to YouTube/TikTok/Telegram. No new Telegram bot is required: Ốp Dev remains the operations contact, PM sends the acceptance link.

The container mounts the staged source read-only and its own marked state directory, has only an internal Docker network, no credentials, and no host service/socket mounts. A small separate Nginx preview proxy exposes the loopback UI and forwards only to the approval service (including WebSockets); the application itself has no external network attachment. Explicit development mode skips dotenv and moves DB/output/queue/OAuth paths to that separate state root. Publishing entry points and scheduler ticks fail before side effects. Do not attach Production credentials or use this fixture service for real publishing.

Readiness requires exact manifest/file hashes, real schema verification, a fresh UI approve/reject against synthetic rows, service health, network/mount inspection and publisher barrier tests. A health response alone is insufficient. `test_dev_runtime.py` exercises the UI through Streamlit AppTest, not a mocked review service. No AI API is used. Leave owner acceptance false until the PO tries the UI.

Updating Dev: stop only `fleet-content-dev`, back up the private Dev SQLite DB, stage the approved full SHA, prepare a new compose file pointing to that artifact and the existing marked Dev state, rebuild/restart only this project, rerun the checks and record a version-bound receipt. Dev never touches the live ContentCreator checkout. Recovery restores the previous compose/artifact and preserves any newer state; database restore is a separate decision.
